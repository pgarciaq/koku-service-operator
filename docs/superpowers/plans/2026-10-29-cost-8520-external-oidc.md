Steps use checkbox (`- [ ]`) syntax for tracking. Every step states WHAT changes, WHERE, and WHY — if a step's reason is unclear, stop and ask instead of guessing.

**Revision notes (2026-10-29, after design review):**

- Added Task 0: provision the non-production Entra fixtures and pick the E2E cluster before coding. Tasks 1–4 can start in parallel with Task 0, but Task 5 cannot run without it.
- Removed all backwards-compatibility/migration machinery: the operator is unreleased, so `spec.auth.keycloak` is replaced outright by `spec.auth.oidc`. Keycloak stays a supported on-prem IDP, configured through the same generic fields (Keycloak profile).
- Locked: Entra `tid` maps to `org_id` with hyphens stripped; `oid` is the stable principal key; `X-Bearer-Token` forwarding is dropped (verified: nothing reads it).
- Added oauth2-proxy session email-claim configuration + tests (Entra rarely emits `email`, and the proxy cannot build a session without a mapped email/username claim).

**Goal:** Replace the Keycloak-specific user-authentication path in `koku-service-operator` with configurable, standards-based external OIDC (first provider: Microsoft Entra ID), while preserving Koku's `X-Rh-Identity`/Insights RBAC contract and Metrics Operator uploads. Cost Management SaaS (console.redhat.com) is untouched: this operator only manages on-prem deployments. On-prem keeps Keycloak as one supported IDP option among Entra, Ping, Okta, and others — all configured through the same generic OIDC fields. `cost-onprem-chart` is deprecated and is not an implementation target; it is only the observed baseline for current behavior.

**Architecture:** Two token flows meet at the Envoy gateway, which is the only component that validates provider tokens:

- Interactive users: browser → oauth2-proxy (OIDC client + session cookie) → nginx (header hygiene) → Envoy (JWT validation + claim mapping) → Koku/Ingress. The proxy logs the user in via the external IDP and forwards the resulting Cost Management API access token; nginx passes through only that proxy-supplied header so a browser cannot spoof credentials; Envoy validates the token and builds `X-Rh-Identity`; Koku authorizes via Insights RBAC exactly as today.
- Machines: koku-metrics-operator → IDP token endpoint (OAuth client credentials) → Envoy → Ingress (uploads) and Sources (validation) using that one token for both calls.
- Identity mapping: `org_id` = Entra `tid` with hyphens stripped (schema-safe, still unique, fits the 36-char field); `account_number` from explicit per-deployment config; principal key = Entra `oid`; admin = configured `roles` value present → `is_org_admin=true` → full existing RBAC `admin_default` bundle.
- Full diagram: `docs/design/COST-8520-external-oidc-design.md` ("Proposed Architecture").

**Tech Stack:** Go, controller-runtime, Kubernetes CRDs, Envoy JWT authentication/Lua, oauth2-proxy, nginx, Ginkgo/Gomega, pytest, OIDC/JWT test fixtures.

**Spec:** `docs/design/COST-8520-external-oidc-design.md`; `docs/design/COST-8520-tdd-test-plan.md`

## Global Constraints

- A deployment using external OIDC must not require a Keycloak instance, Keycloak CR fields, or Keycloak Admin API. Conversely, a deployment using Keycloak configures it through the same generic `spec.auth.oidc` fields (the Keycloak profile); there is no separate Keycloak code path.
- No backwards compatibility for the operator CRD: the operator is unreleased, so `spec.auth.keycloak` is removed and replaced rather than translated. (Deliberate exception: `koku-metrics-operator` IS released and also serves SaaS, so its new scope field keeps `api.console` as the omitted-field default. SaaS behavior must not change.)
- SaaS is out of scope: no change in this plan may alter console.redhat.com behavior. `cost-onprem-chart` is deprecated; the SNO chart deployment is baseline evidence only, never an edit target.
- UI API requests use a JWT access token whose audience is the configured Cost Management API audience; ID tokens are rejected for API authentication.
- Preserve the existing `X-Rh-Identity` output contract and replace, rather than trust, caller-supplied identity headers.
- Preserve Insights RBAC, `ENHANCED_ORG_ADMIN=False`, and the complete `admin_default` bundle when the configured admin role is present.
- Map Entra `tid` to `org_id` with hyphens stripped, only under the one-Entra-tenant-to-one-Cost-Management-org assumption; map `account_number` from explicit config; use Entra `oid` as the stable user/RBAC principal identifier.
- Keep principal provisioning/SCIM outside COST-8520. The existing optional `spec.rbac.keycloakSync` remains a separately gated Keycloak-only capability and is not required for external OIDC login.
- Validate Entra as the initial full-stack provider. Keycloak is supported from the start as a generic OIDC profile. Do not label Okta or Ping full-stack supported until their access-token audience/claims and Metrics Operator grant pass the same conformance checks.
- OAuth `scope` and JWT `aud` are separate contracts. Verify the configured Metrics Operator token against both Sources operations and Ingress upload before claiming provider compatibility.
- Do not log or commit access tokens, refresh tokens, client secrets, or private keys. Tests and live checks retain only safe claim summaries and response status.
- Drop `X-Bearer-Token` forwarding: verified that no on-prem component (Koku, Ingress, operator) reads it, so the new flow does not set it. This only removes a write; nothing can break by its absence.
- One issuer per deployment (locked architectural rule): in every deployment, the browser flow and the Metrics Operator flow always use the same IDP — SaaS console auth, Keycloak, Entra, Ping, or any other — never mixed. Both cut over together; rollback is restoring the previous CR.

## Review Focus

- **Token confusion:** ID token has UI-client audience while API access token has Cost Management audience; only the latter authenticates API requests.
- **Session identity:** oauth2-proxy needs a mapped email/username claim to build its login session; Entra rarely emits `email`, so this mapping must be explicit or browser login fails before any API call happens.
- **Header spoofing:** browser-supplied `Authorization`, `X-Forwarded-Access-Token`, or `X-Rh-Identity` cannot bypass oauth2-proxy or replace Envoy's validated identity.
- **Wrong audience/scope:** a correctly signed token with an unintended audience or insufficient scope is rejected; a requested scope is never treated as proof of `aud`.
- **Service identity elevation:** Metrics Operator client-credentials tokens never inherit the human `org-admin` role or `is_org_admin=true`.
- **Tenant/account ambiguity:** missing, malformed, or mismatched `org_id`/`account_number` fails closed and never selects a shared/default tenant.

## Task 1: Replace Keycloak CRD fields with provider-neutral OIDC (`koku-service-operator`)

**Why this task exists:** today the CRD *requires* `spec.auth.keycloak.url` (root CEL rule), so an Entra deployment is rejected at `kubectl apply` before any pod runs. This task makes generic OIDC expressible and Keycloak expressible only through it. There is deliberately NO translation layer for old CRs: the operator is unreleased, so the fields are replaced.

**Files:**
- Modify: `api/v1alpha1/costmanagementserviceconfig_types.go` — delete `Keycloak` field/types, add `OIDC` struct, replace the CEL rule.
- Modify: `api/v1alpha1/costmanagementserviceconfig_webhook.go` — implement semantic validation of the OIDC profile.
- Test: `api/v1alpha1/costmanagementserviceconfig_webhook_test.go`, `api/v1alpha1/resource_validation_test.go` — red-first cases for every rule below.
- Generated: CRD, deepcopy, manifests, and bundle artifacts per `AGENTS.md` / `CLAUDE.md` (regenerate with `make`, never hand-edit).
- Modify: `config/samples/` — one Keycloak-profile sample and one Entra sample, because users copy samples and untested samples rot.

**Interfaces:**
- Add required `spec.auth.oidc` with `issuerURL` (WHO signs tokens; must be HTTPS because tokens over plaintext HTTP are forgeable in transit), `jwksURL` (WHERE Envoy fetches signing keys; explicit rather than derived because derivation rules are provider-specific), `audiences` (WHICH API the token must be for; at least one, because an empty list would accept tokens meant for anyone), `uiScopes` (WHAT the browser flow requests, including the delegated API scope — without it the IDP returns a token for the wrong audience; a list of scope strings joined with single spaces into the `--scope` argument, flag spelling verified via `--help` per Task 2 Step 4), optional `endSessionURL` (provider logout; optional because local-only logout is a valid choice), `tls.caCertSecretName` / `tls.insecureSkipVerify` (HOW to trust the IDP's TLS; insecure is opt-in only because skipping verification invites machine-in-the-middle token theft), `claims` (HOW provider claims translate to identity), and `serviceIdentity` (business identity for machine tokens, which never contain org/account/user fields).
- `claims` maps `orgID` (claim path holding the tenant ID, e.g. Entra `tid`), `accountNumber` (explicit trusted source per deployment), `principalID` (stable user key, e.g. Entra `oid` — stable across renames, unlike email), `username`/`email` (display only, never used for authorization or principal matching), `adminRoles` (claim path holding role values, e.g. `roles` or Keycloak's `realm_access.roles`), and `adminRoleValue` (the exact string that means admin). Claim references support dot-separated paths for nested claims (dots are path separators with no escaping; claim names containing literal dots are unsupported — none of the target providers use them). WHY dot paths: providers nest roles differently, and hardcoding `realm_access` would reintroduce provider-specific code. A resolved value may be scalar or list: admin matches iff scalar-equals or value-is-in-list (exact match either way); org/principal claims must resolve to a single scalar string or the request fails closed (WHY: silently picking element [0] would invent identity).
- `serviceIdentity` contains the configured `orgID`, `accountNumber`, and non-admin service username used for client-credentials JWTs, plus `tokenMarker` (claim path + expected value proving a token is a machine client-credentials token — e.g. Entra `idtyp` = `app`, Keycloak `preferred_username` = `service-account-<kmo-client>`; values verified from Task 0 fixture tokens). WHY: machine tokens carry no business identity, but Koku requires org/account/user on every request — the gateway must supply them from trusted config, and the username must be visibly non-human so it can never collide with a user principal (convention: e.g. `svc-cost-upload`, no `@`, max 150 chars, documented in `oidc.md`). WHY the marker: header position does not prove token type — a user token presented on the `Authorization` header would otherwise inherit the service identity.
- Delete `spec.auth.keycloak`, `KeycloakSpec`, and `KeycloakTLSSpec` (after confirming no other references). WHY delete instead of deprecate: unreleased CRD, and keeping dead fields invites configuring two profiles at once.
- Replace the root CEL rule so it requires `spec.auth.oidc.issuerURL` (non-empty, HTTPS) instead of the Keycloak URL. WHY CEL rather than webhook-only: CEL rejects bad CRs at the API server with no operator running, which is the fastest possible feedback.

## Task 2: Make readiness and the UI proxy provider-neutral (`koku-service-operator`)

**Why this task exists:** two things break on day one with Entra if left Keycloak-shaped. First, readiness probes a Keycloak-derived JWKS URL, which would block a healthy Entra deployment from ever becoming ready. Second, the browser login flow must (a) request a delegated API scope so the IDP returns an access token for the Cost Management API, (b) build a login session from claims Entra actually emits, and (c) forward the access token (not the ID token) to Envoy.

**Files:**
- Modify: `internal/controller/validation.go`, `internal/controller/validation_test.go` — rewire the readiness probe to the configured JWKS/CA.
- Modify: `internal/resources/ui.go`, `internal/resources/ui_test.go` — render generic oauth2-proxy args and strict nginx header forwarding.
- Depends on: Task 1 (reads the new `spec.auth.oidc` fields) and Task 0 Step 1 (needs the UI client redirect URI + delegated scope string for the live smoke test, not for unit tests).

**Interfaces:**
- Readiness consumes the normalized issuer, JWKS URL, and provider CA settings from Task 1. It must never derive `/realms/{realm}/protocol/openid-connect/certs`, because that path exists only on Keycloak.
- oauth2-proxy remains the session manager and OIDC client; its Secret still contains `client-id` and `client-secret`. This Secret is not a Keycloak server dependency — it is the UI client's credential at whatever IDP is configured.
- UI API requests carry the OAuth access token in `X-Forwarded-Access-Token`, set by oauth2-proxy from its own token response; nginx copies that proxy-supplied value to Envoy. The browser's own `Authorization` and `X-Rh-Identity` values are never forwarded as credentials, because the browser is untrusted input.

## Task 3: Generalize Envoy JWT validation and identity mapping (`koku-service-operator`)

**Why this task exists:** Envoy is the security boundary — it decides which tokens count as API credentials and what identity each one carries. Today the issuer, audience list, and every claim lookup (`realm_access.roles`, `org_id`, `preferred_username`) are Keycloak-shaped, so Entra tokens would be rejected (wrong issuer/audience) or, worse, mapped to a broken identity. This task makes validation fully configuration-driven and the Lua mapping provider-neutral.

**Files:**
- Modify: `internal/resources/envoy.go` — JWT filter generation plus the embedded Lua identity mapper.
- Test: `internal/resources/envoy_test.go` — YAML round-trip tests plus Lua-behavior cases driven through the repo's established harness.
- Integration test: `test/pytest/suites/auth/test_gateway_auth.py` — live gateway assertions against the Task 0 test stack.
- Depends on: Task 1 (reads `spec.auth.oidc` + `serviceIdentity`) and Task 2 (assumes the UI token arrives in `X-Forwarded-Access-Token`).

**Interfaces:**
- Envoy validates the UI access token extracted from `X-Forwarded-Access-Token` and the Metrics Operator token from `Authorization`; each source has its own JWT provider entry with configured issuer/JWKS and its explicitly allowed `audiences`. WHY two entries with separate validated-metadata keys: Lua must distinguish an interactive user token (identity comes from claims) from a client-credentials token (identity comes from `serviceIdentity` config) via the configured service-token marker — never by header position alone — mixing them up would grant a service token user privileges or a user token the service identity.
- The Lua filter consumes ONLY validated JWT metadata (never raw headers). It maps the UI identity from configured dot-separated claim paths, sets `is_org_admin` only on exact match of the configured admin role value, strips hyphens from the tenant claim to form `org_id` (WHY: `org<guid-with-hyphens>` is a hostile Postgres schema name — hyphens require quoting everywhere and today every org_id is a plain token; the stripped 32-hex value stays unique and fits the 36-char field), and always maps Metrics Operator requests to the configured service identity with `is_org_admin=false`.
- For Entra, the intended deployment mapping is `orgID` from `tid`, `accountNumber` from the configured trusted source, and stable `principalID` from `oid`, with display username/email kept separate. WHY `oid` and not email: `oid` is immutable for the life of the user object; emails change on rename/marriage/M&A and would orphan RBAC assignments.
- Envoy replaces any incoming `X-Rh-Identity` with the gateway-built value and no longer sets `X-Bearer-Token`. WHY replace: the client header is attacker-controlled. WHY drop the bearer copy: verified zero readers on-prem, and every extra copy of a token widens the blast radius of a log leak.

## Plan Decisions and Non-Goals

- The first hypothesis is one KMO client-credentials scope/token usable for both Sources and Ingress. Task 5 is the integration gate; do not silently add a second client, secret, token cache, or audience configuration if the gate fails.
- No CRD backwards compatibility: `spec.auth.keycloak` is deleted, not translated. Keycloak remains a supported on-prem IDP configured through the generic `spec.auth.oidc` fields (Keycloak profile). Rationale: the operator is unreleased, so replacement is cheaper and clearer than a dual-profile translation layer.
- The `koku-metrics-operator` scope default stays `api.console` because KMO is released and serves SaaS — that default is released-behavior preservation, not legacy cruft.
- One issuer per deployment: the UI flow and the Metrics Operator flow cut over to a new IDP together; rollback is restoring the previous CR. Mixed issuers (UI on Entra, KMO on Keycloak) are not supported in this iteration.
- The OAuth client Secret remains required for the UI in every provider profile; it contains client ID/secret and does not imply any particular IDP product.
- `spec.rbac.keycloakSync` remains an independent optional Keycloak-only capability. External OIDC deployments leave it disabled; provider-neutral pre-provisioning/SCIM is not implemented here.
- No production changes are planned for Koku, koku-ui, Insights RBAC, Insights Ingress, SaaS, or `cost-onprem-chart`. The chart is deprecated; the SNO chart deployment is baseline evidence only.
- Only a single org mapping per deployment is supported; multi-org from one IDP tenant is a follow-up (gateway-side mapping table in the CR, evaluated in Lua, allowlisting by construction). Direct claim mapping stays the default forever so single-org deployments never require migration.
- No live provider credentials, tokens, secrets, or unredacted token captures may appear in tests, commits, or logs.
